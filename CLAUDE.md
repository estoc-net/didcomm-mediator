# CLAUDE.md

## Commands
- `npm test` — vitest; `npm run typecheck` — tsc for both targets (main config excludes `src/workers`; `tsconfig.workers.json` checks it with workerd types)
- `MEDIATOR_PUBLIC_URL=http://localhost:8080 npm run dev` — Node dev server (identity `did:web:localhost%3A8080`, same default as Workers; `MEDIATOR_DID_METHODS=peer2` for the offline-resolvable method)
- `npm run dev:workers` — wrangler dev, zero setup: keys are minted into the local D1 on first request, identity is `did:web:localhost%3A8787` (the resolver has a loopback-http fallback for exactly this)
- `npm run smoke -- <url>` — full client flow against any *running* mediator (grant → keylist → anonymous forward → pickup → WS live delivery with binary-frame asserts → blob put/upload/Range/renew/delete when advertised); the deploy verification tool
- `docker compose up -d` — production shape (needs `MEDIATOR_PUBLIC_URL`)

## Architecture
- **Hono + TypeScript ESM**, two deploy targets off one protocol layer. `src/app.ts` is the shared wire surface (POST `/` return-route, `/invitation`, `/health`, CORS; no `/.well-known/did` — that was an Affinidi convention, dropped in favor of OOB + plain GET `/`; a did:web identity *does* serve the standard `/.well-known/did.json` + `/did.json`, which is a different, spec-defined thing); its plain GET `/` steps aside on an Upgrade header so each target mounts its own WebSocket handler after it, answers browsers (Accept: text/html) with the human-readable invitation page, JSON otherwise. @estoc/didcomm-node (WASM build of the estoc-net/didcomm-rust fork — it refuses an attachment holding more than one of json/base64/links, which upstream silently reduces to one) does all crypto; the full pack/unpack API is what makes every enc-alg work without the hand-rolled envelope bugs the Affinidi fork had to patch
- **Node target** (`src/server.ts` + `src/index.ts`): @hono/node-server + @hono/node-ws, sessions in process memory (`src/transport/sessions.ts`), SQLite via better-sqlite3
- **Workers target** (`src/workers/`): same app, but **URL-agnostic and one app per origin** — no public URL is configured; `index.ts` keys a `Map<origin, Promise<Hono>>` off each request's origin and `depsForOrigin` derives that origin's identity (default method `web`, so workers.dev and any custom domain are simultaneously live DIDs of one mediator; a rejected build is evicted so a D1 hiccup can't poison an origin). D1Store (lazy CREATE TABLE, no migrations step); live sockets live in one `InboxHub` Durable Object (`idFromName("hub")`) with hibernatable WebSockets — DID + liveDelivery + **origin** ride each socket's serialized attachment (the DO resolves per-origin deps lazily and needs the origin after hibernation, when there is no request to read it from; an attachment without one gets closed with "reconnect"). The stateless Worker reaches it through the `LiveSink` interface (`wantsPush`/`push`); on Node the in-memory `Sessions` implements the same interface
- **didcomm on workerd** (`src/workers/didcomm-wasm.ts`): wrangler `alias` maps `@estoc/didcomm-node` → a shim that instantiates the `@estoc/didcomm` bundler build manually (`new WebAssembly.Instance(mod, { "./index_bg.js": glue })` + `__wbg_set_wasm` + `__wbindgen_start()`); identical API, same wasm. `nodejs_compat` supplies Buffer/node:crypto to shared code
- **Store** (`src/store/types.ts`): all methods async — D1 has no sync API and the protocol layer is shared. **One store implementation, `src/store/sql-store.ts` (`SqlStore`)**: better-sqlite3 and D1 are both SQLite, so schema + every query are written once against the narrowest shared contract — `SqlDriver.batch(statements)`, a list of statements run in order as ONE transaction (D1's only transaction shape; every transactional path fits it). Backends are thin drivers: `BetterSqliteDriver` (src/store/sqlite.ts, `SqliteStore` subclass) and `D1Driver` (src/workers/d1-store.ts, `D1Store` subclass). Schema is ensured lazily on first use (retry on failure). Tables: accounts (row = grant) / keylist (recipient_did PK → owner, exclusive first-come) / messages (TTL + per-account quota) / blobs + blob_uploads (blob-store, below) / identity (single row, the mediator's keys as JSON — `initIdentity` is INSERT OR IGNORE + re-read, so concurrent first mints all converge on the winner). Ownership checks live in the protocol layer, not the store. (Long-lived databases may still carry `pf_*` tables from the removed public-folder relay; the code ignores them)
- `src/didcomm/` is copied lineage from `../didcomm-http` (did-peer-2/4, did-doc, did-resolver); keep fixes in sync. `src/identity-core.ts` is *all* of identity and fully runtime-free: **what is stored is two keys, nothing else** — no DID and no URL is ever persisted (`loadOrCreateSecrets(store)` load-or-mints the store's identity row; `mintSecrets` is WebCrypto, so the same code runs on Node and workerd; `identityFor(secrets, url, methods)` expands to every active name). **One key set, several simultaneous DIDs**: every method's DID derives deterministically from keys + URL, so which are active is config, not storage — `MEDIATOR_DID_METHODS`, ordered ("peer2,web"; first = primary/advertised, rest = aliases; unset means web on both targets — set peer2 for a non-loopback http URL). The peer2 encoding in identity-core is an **invariant**: every boot re-derives deployed DIDs from the keys, so changing it silently renames mediators. All methods share `#key-1` = X25519/keyAgreement, `#key-2` = Ed25519/authentication; secrets are absolutized once per active DID. Dispatch replies *as the DID the envelope addressed* (`ctx.asOwnDid(unpacked.addressedTo)`) — mediate-grant's routing_did and live-delivery pushes use it too. did:web requires an https public URL (resolvers only fetch https; loopback http is allowed for wrangler dev, with a matching fetch fallback in did-resolver), builds its own document from the stored keys — never fetched, the DIDCommContext pins all own docs — and publishes it at the did.json routes
- **Dispatch** (`src/protocols/dispatch.ts`): handlers return `{type, body, attachments?}`; dispatch alone fills id/thid/from/to and packs — replies are sealed to `verifiedFrom` (the DID the envelope proved), never `message.from`. Anonymous senders: `forward` only; unknown types get a problem-report only when there is a proven sender. **return_route is enforced strictly**: a reply is delivered on the inbound connection only if the message carries `return_route: "all"` (HTTP: every POST; WS: once marks `session.returnRoute` for the socket's lifetime, persisted in the DO attachment) — without it the handler still runs but the reply is dropped
- **Squat resistance**: recipient-update add refuses non-DIDs, >2048 chars, any of the mediator's own DIDs (plus the short form of a long-form did:peer:4), and DIDs holding their own account; forward prefers a local account over any binding **unconditionally** — test "delivers to a registered account DID over any squatted binding" pins this
- **Forward** (`src/protocols/routing.ts`; profile is estoc `docs/replica-model/distributed-delivery.md`, the phase-1 mediator envelope and storage profile): syntactic checks only, the inner envelope is never opened — General JWE JSON shape (`isEncryptedMessage`: unpadded-base64url binary members, `protected` decoded by jose, recipients with `header.kid` + `encrypted_key`, unknown members kept), a `base64` carrier decoded strictly and parsed with momoa so a repeated member name is refused (`data.json` arrives already parsed by the DIDComm library, which has folded repeats — nothing to see there), and **no JSON number anywhere** (`holdsNumber`: the library's decimal parsing is inexact, so a number could not be promised to come out as the same bytes over both carriers; it also means the canonical form is never longer than the wire form, so the wire ceiling is the only size check); what is stored and handed over is `canonicalize(envelope)` (RFC 8785). A refusal is a thrown `ForwardRefused` that `app.ts` turns into the HTTP status (400 malformed; 422 for everything account-dependent — unknown `next`, full queue, key conflict — one answer on purpose); a 2xx always means queued. `messages` rows carry `(owner_did, next_did, forward_id)` under a unique index: same key + same bytes = accepted, nothing written, no second push; same key + other bytes = refused, first stays. The answer is the queue's: a live-delivery push that fails after the insert is noted through `HandlerContext.log` and the forward is still accepted. `storeMessage` is one batch (drop an expired holder of the key → quota-guarded `INSERT … ON CONFLICT DO NOTHING` → read the holder back; the fresh row id tells stored from repeated). A database from before the key gains the two nullable columns by `ALTER TABLE` on first use (`keyMessages`); its waiting rows keep NULLs, which a unique index never collides
- **Library errors never leave `src/didcomm/didcomm.ts`**: `unpack`/`packEncrypted` rethrow as `DIDCommFailure` (operation + the library's error kind, no message, no cause) — the library quotes what it was parsing, including headers of an envelope it already decrypted, and every transport logs what it catches
- **Pickup**: one inbox per account; `recipient_did` echoed, never used to scope. Delivery attachments are **base64url**. Live delivery: WS session binds to first proven DID and never re-binds; push leaves messages queued until messages-received
- **blob-store/1.0** (`src/protocols/blob-store.ts` + `src/blobs/`; spec is estoc `docs/blob-store.md`): an agent holding a mediation `put`s `{hash, size}` (hash = sha-256 multihash, base32 lower `b…`, `src/blobs/hash.ts` — no multiformats dep) and gets `put-result {url, retain_until, upload?}`. **A blob is one mediation's**: the row is (owner_did, hash) unique, served at `/b/<id>` where the id is 20 random bytes base32 (`mintBlobId`) — the URL says nothing about the hash or the owner, and the same hash put by two mediations is two rows, two ids, two uploads (no sharing, no dedup; `delete` is final: row and bytes go at once). `upload.url` is `PUT /b/<id>?token=<one-time uuid>` **through the mediator itself** (not a presigned S3 URL — that would need account secrets and break one-click deploy; cost: Workers body limit, so `MEDIATOR_BLOB_MAX_BYTES` defaults to 100 MiB). `BlobStorage` (fs on Node, R2 with the `sha256` put option on Workers) keys bytes by id and is the only place they meet their hash; the DB holds `blobs` (id PK, owner_did — deliberately no FK so purge can still learn the id after the account goes —, hash, size, uploaded_at, retain_until; quota = SUM(size) of live rows; a repeat `put` extends retention, never shortens) / `blob_uploads` (tokens, consumed on claim). GET/HEAD `/b/<id>` with Range to anyone, 404 unless uploaded and still retained. Purge (cron on Workers, the hourly interval on Node) drops rows past retention or whose account is gone, then their bytes. A database still carrying the first schema (hash PK + `blob_holds`, 2026-08-26/27) is reset on first use — `dropOldBlobTables` — its bytes in storage (files/R2 objects named by hash) are the operator's to sweep. Off when `blobDir` is null / no `BLOBS` R2 binding: routes absent, protocol not advertised, `put` → `e.p.blob.refused`. `BlobService` rides `HandlerContext.blobs`; `GET /` advertises `blobs: {retainSeconds, maxBytes, quotaBytes}`
- **OOB invitation** (`src/oob.ts`): out-of-band/2.0 invitation, deterministic id (sha256 of DID) so the QR/URL never changes across boots; `?_oob=` base64url on the public URL, plaintext JWM at `GET /invitation`. Issue-only — no inbound handler, invitations travel as URLs not envelopes; deliberately **not** in `SUPPORTED_PROTOCOLS` (that list doubles as the discover-features disclosure of what you can *send* us)

## Gotchas
- **WS frames are sent as text, received as either**: the DIDComm v2 spec never specifies the frame type, so implementations disagree — Credo sends binary, ACA-Py accepts both. Text frames arrive as plain strings in every environment (browser/RN/Node) while binary arrives as Blob/Buffer/ArrayBuffer, so we send text and tolerate both inbound. Headless ws clients mask frame-type bugs; the demo-interop test and smoke assert `isBinary === false`
- the fork's `new Message()` refuses what the mediator must refuse (multi-carrier attachment data), so tests for those build the JWE by hand — `sealRaw` in `test/helpers.ts` (jose)
- didcomm-node needs `message.from` to match the packing key: test helpers must set `from`/`to` in the plaintext
- didcomm-rust re-serializes JSON with sorted keys — compare forwarded payloads structurally, never by string equality
- `pack_encrypted` here always `forward: false` — the mediator replies directly; wrapping its own replies for another mediator would be wrong
- vitest runs HTTP tests via Hono's `app.request()`, but live delivery needs a real listen + `ws` client (`test/live-delivery.test.ts`)
- tsconfig `rootDir: "src"` and `exclude: src/workers` so Docker's `npx tsc` emits `dist/index.js` without workerd types
- The `@hono/node-server` audit advisory (serve-static path traversal on Windows) doesn't apply: nothing is served statically
